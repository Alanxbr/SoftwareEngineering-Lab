# 实验8：单元测试

## 一、实验目的

1. 掌握 Python 标准库 `unittest` 的组织方式：测试包、测试类、`setUp/tearDown` 与断言方法。
2. 能够针对核心算法、业务规则和接口层设计正常与异常场景的测试用例。
3. 学会用覆盖率工具衡量测试充分性，定位未被覆盖的分支。
4. 体验测试驱动开发（TDD）的红—绿—重构循环，理解"先写测试"对设计的约束作用。
5. 通过测试发现并修复真实缺陷，形成"测试—缺陷—修复—回归"的闭环。

## 三、实验内容与步骤

### 3.1 测试策略

平台分为四层：接口层（routers）、业务层（services）、数据层（dao）和联邦训练层（federated）。单元测试按层设计，遵循"底层重逻辑、上层重契约"的原则：

| 层次 | 测试重点 | 是否启动服务 |
| --- | --- | --- |
| 联邦训练层 | 裁剪、加噪、预算、模型前向与训练、数据生成 | 否 |
| 业务层 | 注册登录、数据集登记、任务创建与启动、权限规则 | 否 |
| 接口层 | 统一响应、状态码、参数校验、鉴权分支 | 进程内 TestClient |
| 数据层 | 由业务层与接口层间接覆盖 | 否 |

测试不对私有函数做白盒断言，只通过公开接口验证行为，这样重构内部实现时测试不需要跟着改。

### 3.2 测试环境隔离

单元测试不能污染演示数据库。`tests/__init__.py` 在导入任何 `backend` 模块之前，把数据目录切到系统临时目录，并初始化一套全新的演示数据：

```python
_MULU = Path(tempfile.mkdtemp(prefix='pingtai_danxiang_'))
os.environ['PINGTAI_SHUJU'] = str(_MULU)
atexit.register(shutil.rmtree, _MULU, ignore_errors=True)

from backend import db, seed  # noqa: E402

db.chushi_hua()
seed.chushihua_shuju()
```

这样每次运行测试都从干净的数据库开始，测试之间也不会相互污染。用户名等可能重复的数据使用 `uuid4().hex[:6]` 生成唯一后缀。

### 3.4 关键用例说明

**（1）L2 裁剪**

裁剪是差分隐私的第一道关口：更新向量范数超过阈值时按比例缩小，不超过时保持原样。测试覆盖三种情况——范数未超、范数超限、零向量：

```python
def test_fanshu_chaoxian_beisuodao_yuzhi(self):
    jieguo = yinsi_fuwu.jiancai([3.0, 4.0], 1.0)
    self.assertAlmostEqual(math.dist(jieguo, [0, 0]), 1.0, places=9)
    self.assertAlmostEqual(jieguo[0], 0.6, places=9)
    self.assertAlmostEqual(jieguo[1], 0.8, places=9)
```

零向量必须原样返回，否则会出现除以零；这一点在异常路径中单独断言。

**（2）拉普拉斯噪声**

噪声用例检查两点：输出维度不变，且结果不等于原向量；ε 为 0 或负数时必须抛出业务异常 4005，防止"无预算也能加噪"的漏洞。

```python
def test_yinsipi_buhefa_pao_yewu_cuowu(self):
    with self.assertRaises(YewuCuowu) as qingjing:
        yinsi_fuwu.jiazao([0.1], 0.0, 1.0)
    self.assertEqual(qingjing.exception.cuowu_ma, 4005)
```

**（3）隐私预算边界**

预算检查最容易出错的是边界：累计值恰好等于上限时允许训练，超过 1e-9 才拒绝。用例同时覆盖 `4.5 + 0.5 = 5.0`（允许）与 `4.8 + 0.5 > 5.0`（拒绝），避免浮点误差导致的误判。

**（4）模型参数往返**

`qu_canshu()` 把 178 维参数摊平，`she_canshu()` 再恢复。测试用随机向量做往返，断言逐元素一致；维度不符时必须抛 `ValueError`，防止静默截断。

**（5）权限规则**

业务层的权限用例不依赖 HTTP，直接构造用户字典调用服务函数：

```python
def test_feichuangjianzhe_qidong_pao_4030(self):
    renwu = xunlian_fuwu.chuangjian(_yonghu('shiyong1'), _renwu())
    with self.assertRaises(YewuCuowu) as qingjing:
        xunlian_fuwu.qidong(_yonghu('shiyong2'), renwu['id'])
    self.assertEqual(qingjing.exception.cuowu_ma, 4030)
```

**（6）接口层契约**

接口测试验证统一响应结构 `{code, message, data}` 与 HTTP 状态码的对应关系，例如未登录返回 `401/4010`、越权返回 `403/4030`、资源不存在返回 `404/4040`、参数校验失败返回 `400/4005`。

### 3.5 测试驱动开发实践

项目主体代码先于测试完成，但为新增功能补做了一次完整的 TDD 循环，验证"先写测试"的工作方式。

**需求**：隐私预算面板需要显示"按当前预算最多可训练多少轮"，原来由前端自行计算，现改为后端统一提供。

**第一步：先写测试**

```python
def test_ke_xunlian_lunshu_xiangxia_quzheng(self):
    self.assertEqual(yinsi_fuwu.ke_xunlian_lunshu(5.0, 0.5), 10)
    self.assertEqual(yinsi_fuwu.ke_xunlian_lunshu(2.5, 0.5), 5)
    self.assertEqual(yinsi_fuwu.ke_xunlian_lunshu(2.4, 0.5), 4)

def test_ke_xunlian_lunshu_eps_buhefa_pao_4005(self):
    with self.assertRaises(YewuCuowu) as qingjing:
        yinsi_fuwu.ke_xunlian_lunshu(5.0, 0.0)
    self.assertEqual(qingjing.exception.cuowu_ma, 4005)
```

**第二步：运行测试，确认失败（红）**

```text
ERROR: test_ke_xunlian_lunshu_xiangxia_quzheng
AttributeError: module 'backend.services.yinsi_fuwu'
has no attribute 'ke_xunlian_lunshu'

Ran 13 tests, FAILED (errors=3)
```

**第三步：实现功能，只写让测试通过的最少代码（绿）**

```python
def ke_xunlian_lunshu(yusuan_shangxian: float, yinsipi: float) -> int:
    """按预算上限估算最多可训练轮数（向下取整）。"""
    if yinsipi <= 0:
        raise YewuCuowu(CUOWU_CANSHU, '隐私预算 ε 必须大于 0')
    return int(math.floor(float(yusuan_shangxian) / float(yinsipi) + 1e-9))
```

同时在 `yusuan_zonglan()` 中增加字段 `ke_xunlian_lunshu`，并补充断言。

**第四步：重新运行（绿）**

```text
Ran 13 tests in 0.003s
OK

Ran 85 tests in 8.650s（当时全量用例数）
OK
```

TDD 的收益在设计阶段就体现出来：先写断言迫使接口必须表达清楚"向下取整"和"ε 非法怎么办"，避免了实现完成后再补文档的随意性。

### 3.8 测试发现的缺陷

**缺陷 001：模拟训练样本数被截断**

平台登记的数据集为 12000 条，但模拟训练实际只使用 1024 条。原因是 `moni.py` 中写死了上限：

```python
yangben = min(max(64, yangben_shu), 1024)
```

复现方式：登记 12000 条样本的数据集，启动模拟任务，对比任务详情中的样本总数与单轮实际参与训练的样本数。预期是 12000 条全部参与，实际只有 1024 条。

修复：把上限改为可配置常量，默认 20000，并支持环境变量 `PINGTAI_YANGBEN_SHANGXIAN` 调低。修复后 27000 条样本、6 轮训练可在 2.72 秒内完成。

**缺陷 002：日志按结束日期筛选漏掉当天记录**

管理员在日志页选择结束日期为当天，查不到任何记录。原因是前端只传日期 `YYYY-MM-DD`，而数据库中的时间为 `YYYY-MM-DD HH:MM:SS`，字符串比较时 `'2026-11-17 19:13:00' <= '2026-11-17'` 为假。

先写回归测试暴露问题：

```python
def test_jieshu_riqi_baohan_dangtian(self):
    jintian = date.today().isoformat()
    jieguo = guanli_fuwu.rizhi(_yonghu('admin'), '', '', '', '', jintian,
                               1, 50)
    self.assertGreaterEqual(jieguo['total'], 1)
```

测试失败（`0 not greater than or equal to 1`），随后在 DAO 层补齐时间：

```python
if len(kaishi) == 10:
    kaishi += ' 00:00:00'
if len(jieshu) == 10:
    jieshu += ' 23:59:59'
```

修复后测试通过，当天日志可正常检索。

## 四、实验小结

1. 单元测试的价值不在数量，而在是否覆盖"容易错的边界"。裁剪阈值、预算相等边界、权限分支、参数维度这些位置，正是缺陷高发区。
2. 环境隔离是测试可重复的前提。把数据目录切到临时目录后，测试可以反复运行，不需要每次手工删库。
3. 覆盖率是参考而非目标。86% 的覆盖率足以说明主流程被验证，但协调器超时、服务重启等场景仍需集成测试补充。
4. TDD 的"红—绿"循环能强迫开发者先想清楚接口语义。先写测试时，函数名、返回类型、异常行为都必须提前确定，这比实现完再补测试更不容易遗漏。
5. 测试与缺陷修复形成闭环：发现缺陷、补回归用例、修复、重跑全量测试，才能保证同类问题不再出现。
