# 实验9：集成测试

## 一、实验目的

1. 理解集成测试与单元测试的区别：单元测试验证单个函数，集成测试验证模块之间、服务与数据库之间、前端与接口之间的协作。
2. 能够设计覆盖完整业务链路的集成测试场景，包括正常流程、权限分支与异常路径。
3. 学会在隔离环境中启动真实服务进程，用 HTTP 客户端驱动测试，保证测试可重复。
4. 掌握缺陷记录与跟踪方法，能写出包含复现步骤、预期结果、实际结果的缺陷报告。
5. 通过回归测试确认缺陷修复没有引入新的问题。

| 项目 | 内容 |

## 三、实验内容与步骤

### 3.1 集成策略

平台由"浏览器前端 → REST 接口 → 业务服务 → DAO → SQLite → 联邦训练线程"多个部分组成。单元测试已经覆盖了各层的内部逻辑，集成测试关注三种交互：

| 交互类型 | 验证内容 | 对应场景 |
| --- | --- | --- |
| 接口与业务 | 请求参数经过校验后能正确落库并返回统一响应 | S4、S5、S6、S13 |
| 业务与训练线程 | 启动任务后后台协调器按轮执行、完成后状态与曲线一致 | S7、S8、S9、S10 |
| 前端与接口 | 静态页面可访问，鉴权与权限在真实 HTTP 上生效 | S1、S2、S3、S14、S15 |

集成测试采用"自顶向下"的链路顺序：先验证登录与鉴权，再登记数据集，然后建任务、启动训练、检查结果，最后验证管理端与异常分支。每一步都依赖前一步产生的数据，任何一环失败都会立即暴露。

### 3.2 测试环境隔离

脚本不以"已经启动的开发服务"为前提，而是自己拉起一个真实服务进程：

```python
shuju_mulu = Path(tempfile.mkdtemp(prefix='pingtai_jicheng_'))
huanjing = dict(os.environ, PINGTAI_SHUJU=str(shuju_mulu),
                PYTHONIOENCODING='utf-8')
fuwu = subprocess.Popen(
    [sys.executable, '-m', 'uvicorn', 'main:app', '--host', '127.0.0.1',
     '--port', '8011', '--log-level', 'warning'],
    cwd=str(JIEGEN), env=huanjing,
    stdout=subprocess.DEVNULL, stderr=subprocess.DEVNULL,
)
```

隔离带来三个好处：不依赖开发者手工准备环境；测试结束后临时库整体删除，不污染演示数据；端口独立，可与开发服务同时运行。脚本在 `finally` 中终止进程并清理目录，即使中途断言失败也不会留下孤儿进程。

### 3.4 关键场景说明

**（1）模拟模式全链路（S6 至 S9）**

创建任务时选择两个数据集、4 轮训练、每轮 ε=0.5。启动后协调器在后台线程执行：每轮模拟各参与方本地训练，裁剪加噪后按样本数加权聚合，写入轮次记录与预算记录。脚本轮询任务状态直到 `yiwancheng`，再分别读取曲线与预算接口做交叉验证：

```python
for _ in range(50):
    _, bao = qingqiu('GET', f'/xunlian/{renwu_id}', lingpai=shiyong)
    if bao['data']['zhuangtai'] == 'yiwancheng':
        break
    time.sleep(0.2)
```

交叉验证的意义在于：状态是"已完成"不代表数据完整。只有曲线轮数等于配置轮数、预算累计等于轮数乘 ε，才能说明训练线程、DAO 与接口三者一致。

**（2）真实模式参与方提交（S10）**

真实模式不自动产生更新，协调器会等待参与方提交。脚本模拟两个数据提供方：先调用 `/kehuduan/renwu/{id}` 领取当前轮全局参数，确认维度为 178，再提交本地更新与样本数；两方都提交后协调器聚合并推进轮次。

这条链路最容易出问题：轮次要匹配、维度要匹配、参与方身份要匹配。任何一项不一致都会返回 4003/4004/4005，因此它也验证了错误码在真实 HTTP 上的表现。

**（3）权限与异常分支（S3、S5、S13、S15）**

权限测试不只看"有没有返回错误"，还要确认错误码与 HTTP 状态码的映射：

| 场景 | HTTP | 业务码 | 含义 |
| --- | --- | --- | --- |
| 未登录 | 401 | 4010 | 未携带或令牌无效 |
| 角色越权 | 403 | 4030 | 当前角色无权执行 |
| 资源不存在 | 404 | 4040 | 任务/数据集/用户不存在 |
| 参数非法 | 400 | 4005 | 字段校验失败 |

前端根据 HTTP 状态码处理登录跳转，根据业务码展示提示文案，两者必须同时正确。

**（4）备份下载（S12）**

管理员创建备份后立即下载，确认返回的是可用的 SQLite 文件而不是空响应。这条用例同时覆盖文件路径校验与权限校验：备份文件名来自服务端返回值，下载接口会拒绝目录穿越路径。

### 3.5 缺陷跟踪

Issue 模板示例（ISSUE-002 节选）：

```text
## 复现步骤
1. 以管理员登录，进入"系统日志"页面。
2. 结束日期选择当天，开始日期留空，点击查询。

## 预期结果

## 原因分析
前端只传 YYYY-MM-DD，数据库时间含时分秒，字符串比较
```

### 3.7 结果分析

1. 15 个场景覆盖了平台的主要链路：从登录、登记、建任务、训练、查看结果，到管理端备份与异常分支。相比单元测试，集成测试更能发现"各层单独正确、组合起来出错"的问题。
2. 真实模式测试暴露了轮次与维度的强耦合：参与方必须使用服务端下发的当前轮参数，否则提交会被拒绝。这类约束在单元测试中难以验证，必须通过真实 HTTP 链路确认。
3. 环境隔离让集成测试可以反复执行。脚本每次使用新的临时库和独立端口，不受开发环境状态影响，这一点比"手工点页面"可靠得多。
4. 局限：尚未覆盖并发场景（多个任务同时训练）、大数据量压力测试和浏览器端交互自动化。这些可以在后续实验或项目中补充。

## 四、实验小结

1. 集成测试的核心不是"再测一遍单元测试"，而是验证模块之间的契约：状态码、错误码、数据一致性、权限边界。
2. 用脚本启动真实服务，比依赖手工环境更可靠。隔离的数据目录与端口让测试可以随时运行、随时清理。
3. 缺陷记录要能让别人复现。复现步骤、预期结果、实际结果、原因分析四部分缺一不可，修复提交号把问题与代码变更关联起来。
4. 回归测试是修复的收尾动作。只改代码不回归，等于把风险留给下一次合并。
